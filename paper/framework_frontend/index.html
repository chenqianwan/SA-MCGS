2. 三项核心贡献

C1 SCC-aware Search Engine

把 SCC 当作循环瓶颈单元处理，而不是让普通 MCTS 在环里展开无限路径。

  • Tarjan SCC localization
  • local window rollout
  • transposition / evidence memory
  • SCC-aware selection and dynamic core
C2 Online Conformal Evaluator

把局部窗口里的高风险或结构冲突转成可累计的发现信号，辅助判断 rollout 是否持续找到证据。

  • OC is a discovery signal
  • not the primary final metric
  • used for convergence analysis
C3 Pluggable Domain Adapters

贡献 3 不再只是固定剪枝策略，而是可插拔领域适配器：主搜索保持通用，领域信息只通过 hooks 注入。

  • record formatting
  • shared risk rubric hooks
  • edge saliency / pruning hints

写作时要强调：Naive 和 SA-MCGS 使用同类通用风险语义；区别不是领域 prompt 开小灶，而是 full-SCC one-shot 与 SCC-aware local search 的机制差异。

3. 关键消融：为什么不能直接全合同 MCTS

TreeMCTS 在 SCC 里的三种失败
  1. Tree explosion: 同一物理节点被展开成不同路径分身，预算被重复路径吃掉。
  2. Rollout trap: 随机游走在环里无法自然结束，只能截断，返回环平均值。
  3. Q-value dilution: 风险节点信号被多条重复路径平均掉，节点间分数差异变小。
SA-MCGS 的处理方式

先把 SCC 从文档图里取出，再在 SCC 内做窗口化探索，最后把结果压缩为一个风险子图节点。

所以 paper 的主流程是：whole document graph → SCC bottleneck → SA-MCGS risk subgraph → collapsed evaluation point。

4. 泛化领域：为什么是这四个数据集

四个域不是为了堆数量，而是覆盖四类真实结构风险：软件依赖、监管披露、成文法引用、商业合同条款。 这让 reviewer 能看到 SA-MCGS 处理的是 cyclic structural risk，不是某个法律关键词任务。

Debian

软件依赖图。 官方 Debian policy 定义 package relationships，例如 depends、pre-depends、conflicts、breaks。

作用：非法律技术域，证明方法不是只对合同/法条有效。

SEC EX-21

监管实体图。 SEC Regulation S-K Item 601(b)(21) 要求披露 subsidiaries、jurisdiction 和 business names。

作用：公司控制链和合并口径风险，连接法律/金融结构。

BGB

权威成文法图。 German Civil Code 是官方法典，条文引用和条件依赖稳定，噪声低。

作用：干净法律域，避免只在噪声合同里“碰巧有效”。

CUAD

商业合同长文本。 CUAD 是 Contract Understanding Atticus Dataset，包含 510 commercial contracts、 13,000+ expert labels 和 41 clause types，且被 NeurIPS Datasets & Benchmarks 接收。

作用：最高噪声、最长文本、最接近真实合同审查；用来测试 one-shot 输出负担和风险端点保留。

6. 章节结构

Abstract
一句话问题、方法、4 domains × 4 models × 80 cases、主结果、压缩率 trade-off。
1. Introduction
从长环结构风险切入：普通 MCTS 在 SCC 中膨胀；one-shot LLM 难以稳定保留多证据；SA-MCGS 将 SCC 坍缩为可搜索风险子图。
2. Structural Risk Subgraph Extraction
定义 record graph、SCC、root/witness/affected、risk subgraph，以及 Root@3 / Risk-any / Risk-all / Compression。
3. Method
按 C1/C2/C3 写：SCC-aware search engine、online conformal evaluator、pluggable domain adapters，再接 dynamic core risk subgraph。
4. Experiments
锁定主实验口径，说明 Naive direct-subgraph baseline、shared risk rubric、公平性和报错计入口径。
5. Results
主表 + SCC size breakdown。核心看 Root@3、Risk-any、Risk-all，不把 Effective OC 当主指标。
6. Analysis
E0/E1/E2/E3：错误处理、输出负担、rollout 收敛、压缩率取舍。
7. Case Study
BGB 长环展示干净法案中的收敛；CUAD 长合同展示高噪声下的稳定性和 one-shot 输出负担。
8. Limitations
成本更高、Risk-all 仍严格、注入 benchmark 有边界、graph construction 质量影响搜索。

8. 分析安排

E0: Error Handling

同时给 strict、valid-only、matched no-error，防止 reviewer 质疑 cherry-picking。

E1: Naive Output Burden

轻量 Naive 在 CUAD 长 SCC 上从 28/32 errors 降到 8/32，但 Risk-all 仍只有 12%。

E2: Rollout Convergence

展示 rollout 增加如何提升 risk coverage / risk-all。Effective OC 只写 discovery，不当主指标。

E3: Compression Trade-off

balanced 更压缩但伤 Risk-all；current/default 更适合 critical 风险主实验。

9. Reviewer 风险清单

质疑回答方式证据
Baseline 是否太弱？ Naive 看完整 SCC，且直接输出 risk subgraph，不是单点弱 baseline。 E1 + main strict
Prompt 是否公平？ 使用通用 risk rubric，不用领域专门找错词；差异来自搜索机制。 E5
是否 cherry-pick？ 文件级锁定主实验；错误计入 strict denominator。 MANIFEST + E0
Compression 下降是否失败？ critical 风险下完整保留风险端点优先；SA 用约 14pt 压缩代价换 Risk-all +31pt。 Main + E3
Effective OC 是否有意义？ 它是累计发现信号，只用于解释 rollout 过程；主指标仍看最终 risk subgraph。 E2

11. 下一步写作顺序

  1. 先改 Abstract + Introduction，把主线写顺。
  2. 把 MCTS-on-SCC failure 消融写成动机，不要只放 appendix。
  3. 写泛化领域和数据集权威性表，解释为什么选择这四个域。
  4. 写 Structural Risk Subgraph Extraction，把指标定义钉死。
  5. 写 Method，按 C1/C2/C3 三项贡献组织。
  6. 写 Experiments + Main Results，严格使用主实验口径。
  7. 写 Analysis + Limitations，主动处理 reviewer 风险。
  8. 最后同步进 LaTeX 并插图表。
